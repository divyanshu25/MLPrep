# Evaluation: exercises

Eleven exercises, easy → hard. Do them on paper first; several are verbatim interview
questions. Solutions are collapsed under each one.

## 1. All metrics from one confusion matrix (warm-up)

A spam classifier on 200 emails produces: TP = 30, FP = 10, FN = 20, TN = 140.
Compute accuracy, precision, recall, specificity, FPR, F1, and the prevalence of spam.
Then: which single number would you *not* report to a stakeholder, and why?

<details><summary>Solution</summary>

- Accuracy $= (30+140)/200 = 0.85$
- Precision $= 30/(30+10) = 0.75$
- Recall $= 30/(30+20) = 0.60$
- Specificity $= 140/(140+10) = 0.9\overline{3}$
- FPR $= 1 - 0.9\overline{3} = 0.0\overline{6}$
- F1 $= 2(0.75)(0.60)/(0.75+0.60) = 0.9/1.35 = 0.6\overline{6}$
- Prevalence $= 50/200 = 0.25$

Don't lead with accuracy: the majority-class baseline ("nothing is spam") already
gets $150/200 = 0.75$, so 0.85 sounds much better than it is. Precision 0.75 is also
alarming for spam specifically — 1 in 4 messages sent to the spam folder is a real
email.
</details>

## 2. Hand-build a ROC curve from 8 scores

Scores and labels, already sorted descending:

| score | 0.9 | 0.8 | 0.7 | 0.6 | 0.55 | 0.5 | 0.3 | 0.1 |
|-------|-----|-----|-----|-----|------|-----|-----|-----|
| label | 1   | 0   | 1   | 1   | 0    | 1   | 0   | 0   |

(4 positives, 4 negatives.) List the ROC points as the threshold sweeps down, and
compute AUC two ways: trapezoid/staircase area, and by counting correctly ranked
positive–negative pairs. Confirm they agree.

<details><summary>Solution</summary>

Each positive = step up by $1/4$; each negative = step right by $1/4$. Label sequence
1,0,1,1,0,1,0,0 gives points (FPR, TPR):

$(0,0) \to (0,\tfrac14) \to (\tfrac14,\tfrac14) \to (\tfrac14,\tfrac12) \to (\tfrac14,\tfrac34) \to (\tfrac12,\tfrac34) \to (\tfrac12,1) \to (\tfrac34,1) \to (1,1)$

Staircase area, column by column (width $1/4$ each, height = TPR during that
right-step): heights $\tfrac14, \tfrac34, 1, 1$, so
AUC $= \tfrac14(\tfrac14+\tfrac34+1+1) = \tfrac{3}{4} = 0.75$... check with pairs.

Pair counting: $4 \times 4 = 16$ pairs. For each positive, count negatives it
outranks: 0.9 beats all 4; 0.7 beats 0.55, 0.3, 0.1 (3); 0.6 beats the same 3; 0.5
beats 0.3, 0.1 (2). Total $4+3+3+2 = 12$, AUC $= 12/16 = 0.75$. ✓ Agrees.
</details>

## 3. AUC under monotone transforms

Prove: if $g$ is strictly increasing, replacing every score $s_i$ by $g(s_i)$ leaves
the ROC curve's points and AUC unchanged. Then answer the trap question: does the same
hold for log-loss? For ECE?

<details><summary>Solution</summary>

The ROC curve is generated by the *sequence of decisions* as the threshold sweeps.
For any threshold $t$ on the transformed scores, $\{i : g(s_i) \ge t\}$: since $g$ is
strictly increasing, it's invertible on its range, and this set equals
$\{i : s_i \ge g^{-1}(t)\}$ — an attainable set under the original scores. Conversely
every original threshold set $\{i : s_i \ge u\}$ equals $\{i : g(s_i) \ge g(u)\}$.
So the two score vectors generate *exactly the same family* of confusion matrices,
hence the same set of (FPR, TPR) points, hence the same curve and area.

Equivalent one-liner via the rank view: AUC $= \#\{s_i^+ > s_j^-\}/(n_+ n_-)$, and
$s_i^+ > s_j^- \iff g(s_i^+) > g(s_j^-)$ for strictly increasing $g$: the pair counts
are identical.

Trap: **no** for log-loss and ECE — both read the *values* of the probabilities, not
their order. $g(p) = p^2$ is strictly increasing on $[0,1]$ but changes every
predicted probability, wrecking calibration and NLL while leaving AUC fixed. That
asymmetry is the whole reason temperature scaling can fix calibration "for free."
</details>

## 4. Precision from prevalence (base-rate algebra)

A disease test has sensitivity (recall) 0.95 and specificity 0.98. Derive the formula
for precision (PPV) in terms of prevalence $\pi$, then evaluate at $\pi = 0.10$ and
$\pi = 0.001$. At what prevalence is precision exactly 0.5?

<details><summary>Solution</summary>

Expected counts per person: $TP = \pi \cdot 0.95$, $FP = (1-\pi)(1-0.98) = 0.02(1-\pi)$.

$$PPV = \frac{0.95\,\pi}{0.95\,\pi + 0.02\,(1-\pi)}$$

- $\pi = 0.10$: $\frac{0.095}{0.095 + 0.018} = 0.095/0.113 \approx 0.841$.
- $\pi = 0.001$: $\frac{0.00095}{0.00095 + 0.01998} \approx 0.045$. A "98% specific"
  test that is wrong 95% of the time it alarms.

$PPV = 0.5 \iff 0.95\pi = 0.02(1-\pi) \iff \pi = 0.02/0.97 \approx 0.0206$. Below
~2% prevalence, most positives are false — with a test most people would call
excellent.
</details>

## 5. F1 vs accuracy vs the degenerate classifier

Dataset: 10,000 examples, 100 positive. Classifier X: recall 0.7, precision 0.5.
Classifier Y: predicts everything negative. Compute accuracy and F1 for both. Then
construct a classifier Z with *higher accuracy than X* but F1 = 0, to show the two
metrics can rank models oppositely.

<details><summary>Solution</summary>

X: $TP = 0.7 \times 100 = 70$, and precision 0.5 means $FP = 70$, so $FN = 30$,
$TN = 9830$. Accuracy $= (70 + 9830)/10000 = 0.99$. F1 $= 2(0.5)(0.7)/1.2 = 0.583$.

Y: $TP=0, FP=0$. Accuracy $= 9900/10000 = 0.99$. Precision undefined (0 by
convention), recall 0, F1 $= 0$.

Z = Y works already if we allow ties in accuracy (0.99 vs 0.99); to strictly beat X,
note X makes $30 + 70 = 100$ errors. Any all-negative-style classifier that also
fixes nothing but makes fewer errors: Y makes exactly 100 errors too, so tie. Make Z
predict negative on everything *except* correctly abstaining is not allowed — so
instead let Z predict positive on exactly one true positive: $TP=1, FP=0, FN=99$:
errors = 99 < 100, accuracy 0.9901 > 0.99, F1 $= 2 \cdot 1/(2 \cdot 1 + 0 + 99)
\approx 0.0198$, tiny but nonzero. For F1 exactly 0 with accuracy strictly above X
you can't do it here (F1=0 forces TP=0, so ≥100 errors); the honest conclusion —
worth stating in an interview — is that Y matches X's accuracy at F1=0, i.e.
accuracy cannot distinguish a useful model from a useless one at 1% prevalence.
</details>

## 6. MSE vs MAE optimal constants, with a twist

For the sample $y = \{2, 3, 3, 4, 88\}$: (a) find the constant predictions minimizing
MSE and MAE respectively (derive, don't just assert); (b) compute each loss at both
constants; (c) a stakeholder says "just remove the outlier." Give one reason each for
and against.

<details><summary>Solution</summary>

(a) MSE: $\frac{d}{dc}\sum(y_i - c)^2 = -2\sum(y_i - c) = 0 \Rightarrow c = \bar{y} = 100/5 = 20$.
MAE: subgradient $\sum \text{sign}(c - y_i) = 0$ needs equally many points on each
side ⇒ any median; with $n=5$ the middle order statistic, $c = 3$.

(b) At $c=20$: MSE $= \frac{(18)^2 + (17)^2 + (17)^2 + (16)^2 + (68)^2}{5} = \frac{324+289+289+256+4624}{5} = 1156.4$;
MAE $= (18+17+17+16+68)/5 = 27.2$.
At $c=3$: MSE $= \frac{1+0+0+1+7225}{5} = 1445.4$ (worse, as expected); MAE
$= (1+0+0+1+85)/5 = 17.4$ (better, as expected). Each constant wins its own loss.

(c) For removal: if 88 is a data error (sensor glitch, unit mixup), it corrupts any
mean-based estimate and should go. Against: if 88 is *real* (an actual huge order,
an actual slow delivery), removing it means your model systematically lies about tail
risk — better to switch to a loss/metric (MAE, quantiles) that encodes how much you
care about tails, than to edit reality.
</details>

## 7. Where bias–variance breaks for 0–1 loss

The squared-error decomposition gives Err = bias² + variance + noise, with variance
always *hurting*. Construct an explicit counterexample for 0–1 loss: a test point
where a *higher-variance* classifier has *lower* expected 0–1 error than a
lower-variance one with the same "average" behavior. Then explain which algebraic
step of the squared-error derivation has no analogue.

<details><summary>Solution</summary>

Test point $x$ with true label 1. Classifier ensemble A (over training draws):
predicts 0 with probability 1 — zero variance, but its "central tendency" is the
wrong label. Expected 0–1 error = 1. Classifier ensemble B: predicts 0 with
probability 0.6, 1 with probability 0.4 — its majority-vote prediction (the natural
"main prediction" for 0–1 loss) is still 0, same as A, but it has *variance*:
sometimes it deviates from its own main prediction. Expected error = 0.6 < 1.
Variance helped, because when your average self is wrong, random deviation from
yourself is your only hope of being right. (In Domingos' 2000 decomposition this is
exactly the sign flip: at points where the main prediction is biased, variance enters
with a *negative* coefficient.)

The step with no analogue: squared error expands as
$(a+b)^2 = a^2 + 2ab + b^2$ and the cross terms vanish under expectation — 0–1 loss
$\mathbb{1}[y \ne \hat{y}]$ has no such bilinear structure; you cannot "complete the
square" on an indicator. There's also no unique notion of "mean prediction" in label
space — you must pick a main prediction (mode), and the clean additive identity is
replaced by one with signed, interaction-dependent terms.
</details>

## 8. Spot the leakage (three pipelines)

Each pipeline reports great validation scores. Name the sin and the fix.

**(a)** Kaggle-style tabular task: `df = normalize(df); select top-50 features by
correlation with y; then 5-fold CV on the result.`
**(b)** Churn model trained on a snapshot: features include
`n_support_tickets_last_90d` and `discount_offered_by_retention_team`; label is
"churned within 90 days of snapshot date."
**(c)** Hospital readmission model: random 80/20 split of *visits*; some patients
have 30+ visits; features include patient ID embedding. Validation AUC 0.91,
new-hospital deployment AUC 0.62.

<details><summary>Solution</summary>

**(a)** Preprocessing-before-split leakage, twice. Normalization using full-data
statistics is the mild version; **feature selection on the full data is the severe
version** — the 50 features were chosen partly for their correlation with the
validation folds' labels, so CV then "confirms" features it helped pick. Fix: put
normalization and selection inside the CV loop (fit on each training fold only). With
p ≫ n this sin alone can turn pure noise into ~0.9 AUC.

**(b)** Target leakage in `discount_offered_by_retention_team`: the retention team
offers discounts to customers *they already believe are churning* — the feature is a
human prediction of the label, often made after the churn signals you're trying to
predict, and it won't exist for fresh customers at scoring time (or worse: acting on
your model changes it — a feedback loop). `n_support_tickets_last_90d` is fine *if*
the 90 days end at the snapshot date; it's temporal leakage if the window overlaps
the label period. Fix: only features computable strictly before the prediction
timestamp; audit any feature that's suspiciously predictive alone.

**(c)** Grouped leakage: the same patient appears in train and validation, and the
patient-ID embedding lets the model memorize individuals ("Bob gets readmitted a
lot") rather than learn medicine. Random-by-visit splitting validates the
memorization. Fix: group split by patient (all visits of a patient in one fold), drop
or carefully handle ID features, and if deployment is at new hospitals, validate with
a *hospital*-grouped split — the 0.91 → 0.62 gap is the measure of what was leaked.
</details>

## 9. Threshold and class weights, quantitatively

Fraud: a missed fraud (FN) costs \$490 on average, a false alarm (FP) costs \$10 of
review time. The model outputs calibrated probabilities.
(a) Derive the expected-cost-optimal threshold and compute it.
(b) Instead of thresholding, a colleague retrains with class weight $w_1 = 49$ on
fraud, keeps threshold 0.5, and reports that "the probabilities look inflated."
Derive the new stationary probability the weighted model outputs for a population
where the true fraud probability is $p$, and show the two approaches make the same
decisions (for a well-specified model).

<details><summary>Solution</summary>

(a) Flag iff expected cost of ignoring exceeds expected cost of flagging:
$p \cdot 490 > (1 - p) \cdot 10 \Rightarrow p > \frac{10}{500} = 0.02$. Threshold
$t^* = \frac{c_{FP}}{c_{FP} + c_{FN}} = \frac{10}{500} = 0.02$, not 0.5.

(b) With weights $w_1 = 49, w_0 = 1$, the weighted CE at a point where the true
probability is $p$ is $-49 p \log q - (1-p)\log(1-q)$, minimized where
$\frac{49p}{q} = \frac{1-p}{1-q}$, i.e.

$$q^* = \frac{49p}{49p + (1-p)}.$$

Now check the decision: the weighted model flags when $q^* > 0.5$, i.e.
$49p > (1-p)$, i.e. $p > 1/50 = 0.02$ — exactly the same rule as (a) with
$w_1/w_0 = c_{FN}/c_{FP} = 49$. So class-weighting + 0.5 threshold ≡ calibrated
probabilities + cost threshold, *in expectation for a well-specified model*. The
practical difference: (a) keeps honest probabilities you can reuse for other cost
ratios and reporting; (b) bakes one cost ratio into the model and destroys
calibration (hence "inflated"). Prefer (a) unless the minority class is so rare the
model needs reweighting just to learn its features.
</details>

## 10. Design the full eval for a fraud model (open-ended, hardest)

You're the ML lead. Transaction fraud, ~0.1% fraud rate, human review team can handle
400 alerts/day out of 2M daily transactions, fraud labels arrive 30–60 days late via
chargebacks. Design the offline and online evaluation. Cover: metric choice, split
design, the label-delay problem, threshold/capacity, comparison protocol for a new
model, and what you'd A/B test.

<details><summary>Solution</summary>

A strong answer touches most of:

**Metric.** Accuracy and plain ROC-AUC are out (0.1% base rate; §2 of notes). The
review team caps alerts at 400/day ≈ top 0.02% of traffic, so the operational metric
is **precision@capacity** (precision in the top-400 daily alerts) and **recall@capacity**
— equivalently a point on the PR curve chosen by the capacity constraint, not by a
probability threshold. Also track $-money-weighted recall (fraction of fraud *dollars*
caught): one \$50k wire ≠ one \$3 coffee. Report PR-AUC as the summary, per-segment
(card-present vs online, new vs old accounts) because aggregate PR hides segment
collapse.

**Splits.** Strictly temporal: train on months 1–10, validate on month 11, test on
month 12. No random splits (temporal leakage; fraud patterns drift adversarially).
Group by account/card as well so an entity's history doesn't straddle the boundary.
Every feature computed as-of transaction time.

**Label delay.** Chargebacks take 30–60 days, so the most recent ~2 months of "not
fraud" labels are censored — recent negatives are unreliable. Options: evaluate on a
window ≥ 60 days old (mature labels); treat recent data as positive-unlabeled; and
monitor a fast proxy label (customer fraud reports) that arrives sooner, knowing it's
biased toward caught-by-customer fraud.

**Threshold/capacity.** The "threshold" is really "rank and take top 400/day."
Calibrate anyway (temperature/isotonic on validation): calibrated scores let you do
expected-loss ranking ($p \times \text{amount}$) and let the business change capacity
without retraining.

**Comparing a new model.** Same test window, paired comparison on the same
transactions; bootstrap the daily precision@400 difference for a CI; multiple seeds
if it's a neural net. Beware winner's curse if many variants were tried — hold out a
final untouched month.

**Online.** Shadow-mode first (score live traffic, don't act) to check score
distributions and agreement; then A/B where randomization unit is the *account* (not
transaction — one account must get a consistent policy, and fraudsters probe
repeatedly). Primary metric: fraud loss per account + review workload; guardrails:
false-positive rate on good customers (declined-transaction complaints, churn),
review-team precision, latency. Caveat to name: **feedback loops** — the new model's
alerts change which fraud gets caught and thus future labels; and blocked fraud is
unobservable (you can't be sure a blocked transaction was really fraud), which biases
naive online precision upward. Long horizon (fraudsters adapt), so keep a small
holdback cell running the old policy if legally/ethically acceptable.
</details>

## 11. Design the eval for an LLM code-review assistant (open-ended)

Your team ships an LLM that comments on pull requests: it flags bugs, risky patterns,
and style issues as inline review comments. Design the evaluation. Cover: how you
build the offline eval set and what you measure on it, how you'd use an LLM judge and
where it will lie to you, and what you measure online. (This is a generative-eval
question — §10 of the notes — so name the reference problem and the judge biases
explicitly.)

<details><summary>Solution</summary>

A strong answer touches most of:

**Frame the axes first.** "Good review" decomposes into: **precision of comments**
(flagged issues are real — false alarms are the product-killer, because developers
tune out a noisy reviewer), **recall on true bugs** (did it catch what mattered),
**severity weighting** (one caught security bug ≠ ten naming nits), and
**actionability/tone** (comment says how to fix, points at the right lines). There is
no single reference "correct review" for a diff — the reference problem (§10) — so no
overlap metric against a historical review; a human reviewer's comments are *a*
sample of valid findings, not ground truth for recall or precision.

**Offline set, two complementary halves.**
(1) *Seeded-bug set for recall:* take clean merged PRs, inject known bugs (off-by-one,
race, null-deref, resource leak, injection…) — now recall has real ground truth:
% of seeded bugs flagged, stratified by bug type and severity. Also run each diff
where possible: a comment that names a bug confirmed by a failing test is
ground-truth-verified, not judged.
(2) *Historical-PR set for precision:* few hundred real PRs, stratified by language,
diff size, and change type. Every model comment gets adjudicated by a human (or a
validated judge) as real-issue / defensible-nit / wrong. Historical human comments
give a *lower bound* reference for what was catchable — but absence of a human
comment must not count as "not a bug" (humans miss things; that's the point of the
product). Report precision, severity-weighted recall on seeded bugs, and comments-per-
PR (noise budget).

**LLM-as-judge, and its lies.** Use a judge to scale adjudication ("is this comment
correct and useful for this diff?"), but name the pitfalls: **plausibility bias** —
the judge scores whether the comment *sounds* reasonable, not whether the bug is
real; ground truth from seeded bugs and executed tests is the antidote, and the judge
is calibrated against a human-labeled sample (~50–100 comments; require ≥85%
agreement before trusting deltas). **Verbosity bias** — long, confident comments win;
control for it in the rubric. **Self-preference** — judge from a different model
family than the assistant. For pairwise system comparison (old vs new assistant on
the same PRs): both presentation orders, paired by PR, Bradley–Terry if more than
two systems.

**Online.** The real labels come from developers: **comment resolution rate** (was
the comment acted on before merge — the accept/dismiss signal), thumbs/"resolve as
not useful" rate, comments-per-PR trend (noise), and guardrails: time-to-merge (a
noisy reviewer slows everyone), opt-out/disable rate per team, and escaped-defect
rate (bugs found in code the assistant reviewed — slow, but the metric that matters).
Randomize by *repo or team*, not by PR — reviewers develop trust or fatigue across
PRs, and one team seeing both behaviors contaminates both arms (§9's unit-of-
randomization logic). Caveat to name: resolution rate is a proxy with a feedback
loop — developers stop reading a reviewer they distrust, so falling resolution can
mean worse comments *or* burned trust from an earlier noisy version; audit with
periodic human review of a comment sample.
</details>
